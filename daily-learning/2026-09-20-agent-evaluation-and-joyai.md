# 从 Agent 评测到 JoyAI 实时视频交互评测

> 学习日期：2026-09-20  
> 来源：Agent 评测公开课程内容 + JoyAI-VL-Interaction 公开仓库、模型卡与项目页  
> 说明：本文是公开资料基础上的学习总结和方法迁移，不代表任何公司内部 SOP，也不声称作者参与过 JoyAI 的研发或评测。

## 一句话理解

Agent 评测不能只看最终回答，而要同时看任务是否完成、执行过程发生了什么、外部环境是否真的改变，以及系统能否稳定复现。对 JoyAI 这类实时视频交互系统，还必须把“什么时候说话、什么时候沉默、什么时候委托”纳入评测。

## 一、六个基本评测对象

| 对象 | 含义 | 在 JoyAI 中的例子 |
| --- | --- | --- |
| Task | 一项有明确输入和成功标准的任务 | 监测跌倒并在规定时间提醒 |
| Trail | 同一任务的一次独立运行 | 同一段视频的一次完整推理 |
| Transcript | 一次运行的完整轨迹 | 视频帧、Speak/Silent/Delegate、语音、工具调用和返回结果 |
| Outcome | 任务结束后的真实外部状态 | 是否真的及时报警、完成计数或触发通知 |
| Grader | 检查某一维度的评分逻辑 | 延迟、漏报、视觉忠实度、沉默质量 |
| Evaluation Harness | 准备环境、批量运行、记录轨迹、评分和汇总的基础设施 | 视频回放、流式推理、时间戳记录和报告生成 |

需要区分 Agent Harness 和 Evaluation Harness：前者负责让模型调用工具、维护状态并持续行动；后者负责测试这套组合体到底表现如何。评测对象不是孤立的模型，而是“模型 + Prompt + 工具 + Harness + 环境”的完整系统。

## 二、Outcome 优先，但不能丢掉 Transcript

Outcome 回答“任务到底有没有完成”，Transcript 回答“为什么成功或失败”。

以 JoyAI 的跌倒提醒为例：最终输出“检测到有人跌倒”并不等于任务成功。还需要检查：

- 事件是否真的发生；
- 是否在规定时间内报警；
- 是否误把坐下或弯腰识别成跌倒；
- 是否重复报警；
- 是否成功触发后续通知；
- 网络、TTS 或前端是否造成额外延迟。

如果模型识别正确但 30 秒后才说，Outcome 仍然不合格。如果模型漏报，也要通过 Transcript 判断是视觉没看见、事件理解错误、选择了 Silent，还是系统链路丢失了输出。

## 三、三类 Grader 的组合

### 1. Code-based Grader

适合客观、可重复的检查：

- 事件是否在时间窗口内触发；
- 延迟、Token、成本和工具调用次数；
- 计数误差；
- 是否重复报警；
- 是否调用了正确的后台 Agent；
- 数据库、文件或工单状态是否真实改变。

### 2. Model-based Grader / LLM Judge

适合开放性较强的内容质量判断：

- 回答是否符合视频内容；
- 是否完整回答任务；
- 是否存在视觉幻觉；
- 语气和长度是否适合场景；
- 生成的解释是否有证据支持。

模型评分需要人工抽检和校准，不能直接当作绝对真值。

### 3. Human Grader

适合主观体验和高风险判断：

- 什么时候说话最合适；
- 是否打扰用户；
- 报警是否清楚、可信；
- 讲解节奏是否自然；
- 失败时是否应该升级人工。

成熟的组合通常是：能用代码验证的 Outcome 交给代码，开放性内容交给经过校准的 LLM Judge，再用少量人工评审持续检查评分质量。

## 四、四类 Agent 的评测重点

不同 Agent 的成功标准不同，不能用同一张评分表：

- **Coding Agent**：代码能否运行、单元测试是否通过、旧功能是否被破坏；
- **Conversational Agent**：动作是否真实完成、状态和金额是否正确、沟通是否合适；
- **Research Agent**：事实是否有来源、关键问题是否覆盖、数字是否准确、来源是否权威；
- **Computer Use Agent**：页面成功不代表任务成功，还要核查后台数据、文件、系统配置或订单状态。

JoyAI 更接近“实时视觉交互 Agent 系统”：它要评测的不只是语言回答，还包括视觉触发、持续观察、沉默、委托和环境状态变化。

## 五、Pass@k 与 Pass-to-the-k

Agent 有随机性，一次成功不能证明可靠。

- **Pass@k**：尝试 k 次，至少成功一次的概率，适合允许多方案探索的任务；
- **Pass-to-the-k**：连续 k 次都成功的概率，适合要求稳定复现的任务。

如果单次成功率是 75%，连续三次都成功的概率约为：

```text
0.75 × 0.75 × 0.75 ≈ 42%
```

因此，创意讲解可以看 Pass@k；监控预警、持续计数和实时翻译更应该关注 Pass-to-the-k、漏报率和最差表现。

## 六、Capability Eval 与 Regression Eval

- **Capability Eval**：回答“这个版本现在能做到什么”，应保留暂时做不好的困难题，才能观察能力是否增长；
- **Regression Eval**：回答“以前会做的事情现在是否仍然稳定”，用于防止修复一个问题时破坏已有能力。

对 JoyAI 来说，版本升级后既要看是否提高了危险事件召回率，也要检查是否导致弯腰误报、无事件时频繁说话或实时翻译漏句。

## 七、迁移到 JoyAI 的最小评测框架

### Task 示例

```text
Task: 监测视频中的人员跌倒，并在事件发生后 2 秒内发出一次明确提醒。
正例：真实跌倒
困难正例：缓慢跌倒、遮挡、弱光
相似负例：坐下、弯腰、躺到床上
```

### 需要记录的 Transcript

```text
事件发生时间
视频帧变化
Speak / Silent / Delegate 决策
模型文字输出
ASR 输入与 TTS 开始时间
后台 Agent 委托与返回时间
前端实际播报时间
```

### 需要计算的 Outcome 指标

- 事件召回率；
- 漏报率；
- 误报/小时；
- P50/P95 报警延迟；
- 重复报警率；
- 任务完成率；
- 委托成功率；
- 视觉忠实度；
- 沉默准确率。

## 八、从零搭建评测的实际起点

不需要一开始就做几百条任务。可以先从 20–50 条真实任务开始，并让每条任务的判断标准足够清晰。优先从用户反馈、Bug 记录、支持工单和真实失败案例中提取任务，因为真实失败比凭空想象的测试更接近产品风险。

一个可执行的最小项目是：

1. 建立 10 条 JoyAI 实时视频任务；
2. 每条任务准备正例、困难正例和相似负例；
3. 重复运行 3 次；
4. 记录完整时间戳和 Speak/Silent/Delegate；
5. 用代码检查延迟和触发结果；
6. 用人工或 LLM Judge 评价内容与体验；
7. 整理 3 个 Badcase；
8. 写出下一版本的优化建议。

## 我的岗位理解

多模态产品评测不是给最终答案打分，而是把模糊的“效果好不好”拆成：

```text
明确场景
→ 定义成功标准
→ 设计可复现 Task
→ 记录完整 Trail 和 Transcript
→ 验证真实 Outcome
→ 多种 Grader 组合评分
→ 定位 Badcase
→ 提出数据、模型或交互优化
→ 回归验证
```

这套方法可以迁移到实时视频、图像生成、RAG、Computer Use 和业务 Agent，只需要根据任务改变 Outcome 和 Grader。
